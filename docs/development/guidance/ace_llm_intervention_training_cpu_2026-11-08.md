# Actual-tokenizer preparation of the complete artificial batch

The next allocated stage prepares the full saved four-record artificial batch
with the original Qwen tokenizer. It uses the accepted runtime archive on CPU
resources. It does not construct a model, call a CUDA API, update weights or
obtain any new environment response. The 32 training and 24 development worlds
remain ungenerated.

The new entry point authenticates its fixed batch, full project source closure,
model and tokenizer bytes before preparation. The isolated child loads captured
project source bytes and checks the actual copied runtime before and after
preparation. Its output retains all four records, four SFT steps, two DPO steps,
ties and unused strict pairs. Checkpoints are fixed after SFT and final DPO.
The parent independently checks saved bindings, token and exposure counts,
runtime observations and process cleanup. Neither a successful child nor these
metadata checks alone establish scheduler completion or scientific benefit.

The resource proposal is two CPUs, 6 GiB and ten minutes on acpu/cpu-normal,
account ucb736_asc2, without GPU or requeue. CPU04 used the same resources for
77 seconds, including 39.082 seconds staging and two fresh import/tokenizer
sessions. This stage has one session with an expanded source closure. The
580-second supervisor and 180/185-second child bounds remain fixed. Prior batch
RSS was near the memory request, so this is not a claim of comfortable headroom.

Six new boundary methods passed in 0.069858 child CPU seconds, 0.073316542 elapsed
seconds and 26,460,160 peak RSS bytes. They use saved artificial data and fabricated
token IDs. They do not execute the Qwen tokenizer or repeat prior bridge tests.
This is separately scoped preparation cost, not whole-cycle CPU usage.

Implementation review and packet review must close before the exclusive launch.
