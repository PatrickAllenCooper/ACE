# GPU CPU-preflight recovery — independent operational design review

**Disposition: the CPU-first separation is defensible, with three required design refinements below.** Prefer reusing the existing launcher-side CPU metadata verification over allocating a new CPU Slurm stage. Prefer a new GPU02 control/submission/input root with exclusive first creation of the frozen, previously absent `GPU01/gpu` subtree over rewriting frozen scientific commands. These are design recommendations, not implementation approval, failure/no-work acceptance, or execution authorization.

## Required refinements

**R1 — Move the complete historical-check call graph, including the end-of-run predicates.** Replacing only entry lines 198/200 is insufficient. `authenticate` is called before staging and again after same-PID exec (main 653–684). `run_controller` then calls `campaign._load_attempt` for all five CPU policies (538–542). Each `_load_attempt` inventories its entire attempt tree (campaign 294–315, `_inventory` 145–149), and each of the three `run_policy(... phase='gpu')` calls repeats those five CPU loads (campaign 204–209; GPU phase 455–456). There are thus five CPU attempt scans in the controller plus five before each GPU policy on the normal path, with possible further barrier calls when retaining unstarted policies. The first service is created only afterward (campaign 223–233).

The same two full historical trees are hashed again at entry 598–602, before the final deadline check at 604. Keeping these scans on the GPU after removing startup scans merely relocates the bottleneck into the final window. Move **historical** full-tree verification to CPU-side before/after custody and provide the narrow accepted-history admission described in R2 for all CPU-policy barrier calls. Preserve the ordinary `_load_attempt`, inventory, runtime and raw-service validation for **new GPU attempts** (GPU phase 425–433; entry 579–597; service-evidence 234–274). No global replacement of `_inventory`, no unconditional `_load_attempt` bypass, and no weakening of failed/unstarted GPU evidence.

The resulting terminal must state that historical post-custody verification is external/pending; `scientific_qualified=false` already exists and alone does not disclose the removed predicates. Independent actual acceptance must compare all original noncampaign CPU files and the original campaign map, allowing only the three declared GPU policy subtrees. A failed/partial/missing post-check blocks acceptance and preserves all generated evidence. It must not induce another GPU run.

**R2 — Bind and consume an authenticated small read set; a receipt does not freeze a tree.** The original CPU acceptance supplies independent bundle/terminal/attempt pins and full file maps. A preparation must bind that acceptance, exact roots, complete file membership, before/after byte maps, source and failure lineage, and the independently authenticated directory roster where required. Root inode/stat identity alone cannot freeze descendants. The old `inventory` traverses directories and rejects symlinks/nonordinary entries, but returns only a file-hash map; do not misdescribe it as an exact pinned empty-directory-roster comparison.

For the CPU phase barrier, retain the original structural/identity/success checks using independently pinned bytes: bundle and phase terminal, five attempt/candidate pairs, their 120 referenced arm receipts, campaign and source-plan records. For this fixed campaign the five CPU policies have no persistent service; preserve the service-absence check. If that precondition changes, fail rather than accepting new closure paths. Attempt/arm pins must descend from the accepted CPU record, never from hashes freshly inferred from live `attempt.json`. Campaign `run_policy` line 209 currently supplies a live self-hash and explicitly calls this a local barrier, not independent admission; it cannot become the authority for a cached fast path.

Use stable bounded no-follow reads of the exact metadata, then decode/use those **same bytes**, or consume an independently pinned captured read-set buffer. Do not hash a path and reopen it unpinned later. The in-memory campaign/plans are already anchored to the pinned CPU bundle; preserve that path. Restrict the admission adapter to the exact five accepted CPU policy IDs, paths, campaign/source-plan identity and expected receipt hashes. Unknown policies/paths/pins must fail; new GPU policies must continue through the unchanged full evidence validator. Directory/symlink/root checks and exclusive new-attempt creation remain live guards.

A full-tree receipt plus final custody does not prove that arbitrary mutable files were unchanged between observations. With every decision/admission read confined to pinned captured data, unused historical-byte drift can block final acceptance without changing GPU decisions. This is an explicit change in **when historical custody is verified**, not proof of continuous filesystem immutability. If a caller retains an unpinned live historical read, preserve its at-use check or provide a protected, byte-identical read view. A checksum manifest, chmod by the same owner, a symlink, or a hardlink farm is not an immutable view. A full historical copy is unnecessary when the small consumed read set can be captured and the remaining bytes are custody-only.

**R3 — Adopt one precise recovery-root contract across all coordinators/consumers.** The original builder 489–518 binds `cpu-launch-packet.future_gpu_output`, three launch contracts, old persistent argv and service identities to GPU01/gpu. Entry 387–406, launch-shim 105–137/146–167, persistent client 247–257 and paired-arm 158–163 enforce those joins. A new output URI cannot silently replace them: changing contract bytes changes argv pins embedded in the immutable campaign. A typed relocation would require an explicit reviewed logical-to-physical command/path derivation and matching runtime/custody validators; merely changing `ROOT` or setting a policy object's command field to the historical string is not acceptable provenance.

The parent's **absent-subtree alternative is the smaller defensible design**. Entry `validated_output` 630–651 and `authenticate` 315–324 require separated CPU inputs/output, GPU inputs/output; they do not require GPU inputs and GPU output to share a parent. GPU02 inputs can therefore remain in the new exclusive control root while `gpu_output` stays the original frozen GPU01/gpu URI. Service contracts, campaign digest, commands, seeds and model/checkpoint identities need no relocation for that choice.

That alternative requires all of the following in the explicit recovery authority and implementation:

- Finish and independently accept GPU01's failed full custody/no-work proof first. Preserve its sealed archive, both local capsules, packet, intent/result, scheduler failure and original files permanently. No mutation while the current collector owns the roots/locks.
- Bind the exact failed-job/source/packet and accepted full original inventory, original namespace, new control root and the **one** authorized append subtree. Change the proposal's blanket no-old-root-mutation statement to immutable original files/membership outside this subtree. Parent directory timestamps necessarily change; this is not a byte-identical whole-tree claim after append.
- Under both locks, reconcile the actual terminal accounting/journals and absence of active/ambiguous ACE attempts. Verify original GPU01 files unchanged and reject `lexists(GPU01/gpu)`, including a dangling symlink, any GPU service/controller/attempt marker, and CPU campaign policy-05/06/07 or finalization markers. Establish absence again immediately before the once-only submission. The allocated worker must create the subtree exclusively; do not precreate it to manufacture an ownership receipt.
- Use only GPU02's new intent/result, log paths and input pins for the new job. Its GPU output records must identify GPU02's packet/admission and actual job even though the path contains `_01`. Do not reinterpret GPU01's failure or submission as the new success. Any new ambiguity or existing output bars automatic retry.
- Amend the builder's output argument (`ROOT+'/gpu'`, 652), admission, launcher absence/sibling-root gates (95/128), monitor (39–49), collector and finalizer location assumptions explicitly. The old launcher's blanket sibling-GPU-root prohibition must become an exact accepted-failure exception, not a wildcard bypass. Collect both the new control root and appended old output root, and compare the old root outside `gpu/` to its accepted failed inventory. Do not double-count overlapping custody or charge the failed job again.

## Minimal CPU-first mechanism

Reuse the existing coordinator's exhaustive CPU-tree checks before GPU allocation. Factor their observations and small authenticated read set into preserved preparation evidence instead of running an additional study merely to create a receipt. The parent reports roughly 784 seconds in readiness and 250 seconds in final reconciliation; those are planning observations supplied for this design, not measurements repeated or independently established here. Retain bounded metadata work, ownership, failure evidence and the final exact queue/journal/namespace gates.

The simplest authority chain is to publish the preparation evidence before freezing GPU02 inputs, independently review its actual bytes, then include its receipt/acceptance/capture pins in the new packet and committed bootstrap arguments. Reuse the existing observed verification rather than rescanning just to produce a second report. Later safety reconciliation remains distinct. If preparation instead completes inside the launch invocation, the new packet must explicitly authorize a narrow execution binding that identifies the accepted CPU baseline, verifier source, roots/full-map expectation, output capture and actual receipt digest; that digest must be carried into the exclusive intent and authenticated GPU command. A hash read from the receipt itself, a mutable path, an unpinned environment variable, or a bare `verified=true` is not independent binding. If separate review of the actual record is required, stop the prepare-only phase before submit and resume only with its exact pinned disposition; no automatic inferred acceptance.

Keep staging complete by original start+120, first verified GPU work by start+240, service startup120/freshness90, work2820/final2860, service cap1200/reserve600 and allocation2880 unchanged, including across same-PID exec. Measure the narrowed metadata read set during existing CPU preparation; removal of the observed historical-I/O blocker alone does not prove runtime/model loading will fit. Never compensate by extending an idle GPU window.

Only new affected artificial qualification is needed: reject forged/incomplete/wrong-root preparation and self-derived pins; demonstrate changed read bytes fail or that an independently authenticated buffer remains the sole input; verify historical fast paths cannot apply to GPU attempts or finalization; preserve symlink/parent-rebinding/exclusive-output behavior; reject existing or ambiguous GPU01/GPU02 markers; bind output to the actual new job; ensure missing/changed post-custody prevents acceptance. Tests and exact implementation review remain future work; none were run here.

## Budget and limits

Pending full failure reconciliation, the observed failed allocation adds 980 CPU/245 GPU seconds to the accepted 29,261/2,505: provisional closed **30,241 CPU / 2,750 GPU**, or 33,841 CPU including the single 3,600 preparation allowance. Without a new CPU allocation, adding GPU02's 11,520 CPU/2,880 GPU cap and finalizer2,400 gives **47,761 CPU / 5,630 GPU**. Reuse of launcher-side metadata does not create a fictitious Slurm job or a second blanket preparation allowance.
