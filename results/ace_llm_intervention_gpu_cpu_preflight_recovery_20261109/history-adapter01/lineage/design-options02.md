## Preserve the original scientific paths

A new exclusive GPU02 control, input and submission root can preserve the frozen service-output URI beneath GPU01 by creating only its previously absent `gpu` subtree. This would append separately identified recovery evidence without overwriting any original file. It avoids rewriting three launch contracts, 24 paired plans, campaign digests or the CPU acceptance. The original failed root must first have a complete, independently verified CURC backup. A precise recovery authority must list the immutable predecessor map and the sole allowed new subtree. Both roots and every original journal remain in terminal custody. Any existing output, service marker, GPU policy attempt or ambiguous/running allocation rejects recovery.

This is an alternative to relocating the frozen service contracts. It is not permission to relabel the first packet as a success or overwrite its source, intent, result, log or archive. The draft supersedes proposal01's overbroad prohibition on every addition under the old root only if independently reviewed and explicitly adopted.

## Separate historical checks from GPU execution

The existing launch coordinator already authenticates full historical trees on CPU before allocation. Prefer binding that exact verification to a new explicit receipt over allocating a second job that repeats it. The receipt must be captured after fresh journal and namespace reconciliation, independently pinned in the submission, and checked against the new packet and original CPU/failure acceptances. It is a record of a completed check, not a promise that the live filesystem is immutable.

Three sources of repeated historical scans need separate disposition: the two inventories in `admit_cpu`, the five original CPU `_load_attempt` calls whose bodies inventory their full trees, and the two historical inventories at the end of `run_controller`. The two authentication calls before and after same-PID runtime staging must use the same pinned preparation. No startup clock is reset. All resource limits, staging120, first-GPU240, service startup/freshness and work/final deadlines remain.

The corrected child must still authenticate every consumed bundle, campaign, attempt header, arm receipt, source, input, checkpoint and runtime object at use or use an already authenticated captured buffer. A separately authored admission check can retain the CPU attempt identity/status/arm predicates while relying on full prelaunch historical inventory verification for unused historical payloads. Its equivalence and exact consumed-file set require review. The original campaign implementation remains byte-identical for scientific execution and final reporting.

Full historical maps are verified again after the GPU allocation, before any execution acceptance, finalizer or utility claim. The child terminal remains explicitly provisional and cannot substitute for that check. Runtime/service validation and new GPU attempt evidence remain required. Any discrepancy is a failed attempt, never a dropped world or rescued result.
